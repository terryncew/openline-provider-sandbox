## 1. olp-wire-canon SPEC.md

**Receipt kinds** (capture layer, §1): `trace_receipt`, `coherence_input_receipt`, `amendment_receipt`, `capture_loss_amendment`. A `coherence_input_disclosure` sidecar travels unsigned alongside a `coherence_input_receipt`.

**Canonical byte construction** (§2–3): A receipt is one JSON object. The signed body is the receipt after removing exactly two top-level members: `payload_hash` and `signature`. Body MUST contain `kind`, `receipt_version`, `algorithm_id`, `canonicalization_id`, `spec_uri`, `attestation`, `capture_status`. `payload_hash` is lowercase hex SHA-256 over the canonical JSON bytes of the body.

**Canonicalization** (`olp-canonical-json-int-v1`, §3): null/booleans/strings/arrays/objects plus integers in [-9007199254740991, 9007199254740991] only; floats and non-finite forbidden; ASCII object keys; parsers must reject duplicate keys; output sorts keys by ascending ASCII code point, no insignificant whitespace, non-ASCII chars as lowercase `\u` escapes, shortest escapes for quote/backslash/standard control escapes, final byte sequence ASCII. OTel capture profile normalizes out-of-domain values via `{"$int":"<canonical decimal>"}` and `{"$f64":"<16 lowercase hex chars>"}` (IEEE-754 binary64, network byte order). Signed receipt bodies MUST themselves remain valid canonical JSON.

**Hash algorithm**: SHA-256 everywhere; 64 lowercase hex chars. OTel Merkle tree per `rfc6962-mth-sha256-promote-odd-v1`: leaves `SHA-256(0x00 || canonical_json(record))`, pairs `SHA-256(0x01 || left || right)`, odd node promoted unchanged, empty root = SHA-256 of empty string. Span records ordered by `(start_time_unix_nano, span_id)`; compact receipt carries only `trace_root`.

**Signature** (§2, §4): Ed25519 only. `signature = {"algorithm": "Ed25519", "public_key": "<32-byte lowercase hex>", "value": "<64-byte lowercase hex>"}`. Signature is computed **directly over the canonical body bytes** — not over `payload_hash`, not over the full envelope. §4 restates in characters: public keys 64 lowercase hex chars, signatures 128 lowercase hex chars. One attestation value defined: `self` (signer says what it observed; proves key possession + integrity, nothing else). One capture status: `provisional`. Root closure, grace intervals, process separation, or use of an OTel Collector MUST NOT silently upgrade either label.

**Amendment/chaining** (§7): initial receipt immutable. Every amendment carries positive `amendment_sequence` + `previous_receipt_hash`; seq 1 references the initial receipt's `payload_hash`; later amendments reference the immediately preceding amendment's `payload_hash`. Verifier MUST reject gaps, duplicate sequences, hash discontinuities. `amendment_receipt` commits a late span via `late_span_hash`; `capture_loss_amendment` commits new + cumulative dropped-span counts (loss accounting applies only to the identified trace). Amendments extend the record; they never make initial capture complete. Derived layers (COLE measurement, controller proposal, governance decision) MUST be signed separately, SHOULD reference input `payload_hash`, and MUST NOT alter the capture receipt's body, trust label, or capture status.

**Schemas** (`schemas/`): `envelope.schema.json` (required: kind, receipt_version, algorithm_id, canonicalization_id, spec_uri, attestation, capture_status, payload_hash, signature), `trace-receipt.schema.json`, `coherence-input-receipt.schema.json`, `coherence-input-disclosure.schema.json` (required: kind, disclosure_version, trace_id, semantic_graph, signal_schema_id, signals), `amendment-receipt.schema.json`, `capture-loss-amendment.schema.json`.

## 2. receipt-gate

### PORTABLE_STANDING_CLAIM.md
This is the frozen study claim for KILL-SWITCH-RECEIPT-INTEGRATION-001, not a reusable standing-claim schema. Its semantic content:
- **Portable owner-STOP = the existing owner-signed terminal standing**: `MandateOwnerView` head → `REVOKED` for the covered mandate slot, or `ReceiverStandingView` head → `INACTIVE` for the covered action, admitted through the existing `admit` successor rules. No new authority machinery, store, or wallet change.
- **"Current standing"** = the receiver-admitted head of a monotonic successor chain (per `docs/MANDATE_OWNER_001.md`: `ACTIVE` = exact bound mandate current; `REVOKED` = slot has no current executable mandate authority; an ACTIVE head superseded by a newer ACTIVE head is historically authentic but implicitly superseded, never false). `docs/STANDING_SEAM_001.md`: a standing projection is signed, names the hash of the support artifact and of the exact protected call, carries a sequence + predecessor, has its own freshness window; the receiver admits it only against a receiver-pinned issuer key and a continuous successor chain; at authorization time the supplied projection must equal the receiver-admitted head — a stale (even perfectly signed) projection no longer matches. INACTIVE translates to revoked-permission evidence; malformed/forged/stale/non-current translates to unverified evidence.
- **STOP_EFFECTIVE** = the monotonic head sequence at which the terminal state was admitted. Ordering is mechanical (monotonic `commit_seq` vs monotonic head sequence), never wall-clock.
- **Who signs**: the owner (owner-signed terminal standing; mandate owner key pinned by the receiver outside the mandate object per MANDATE-OWNER-001).
- **Revocation semantics**: current owner revocation causes old worker authority to be refused without rewriting historical receipts. The final-authority standing check runs inside the same ledger serialization region as permission consumption (compiled/preliminary authorization explicitly non-authoritative at finalize time). **Fail closed**: if standing cannot be established at finalization, the effect does not commit and the inability to check is journaled. The attempt journal binds (commit_seq, stop_effective_seq, outcome) and carries STOPPED / ESCAPED / UNKNOWN path verdicts plus PRE_STOP_COMMIT ordering classification; an independent appraiser can re-derive every verdict from the journal + standing admission history via `olp_gate.stop_standing.derive_path_verdicts` without trusting the live system.

## 3. kill-switch `portable/`

### GATE_CONTRACT.md — authority → proposal → final check → effect → evidence
Authority is **owner-controlled STOP**: worker and ordinary receivers cannot create, clear, decrease, or restore STOP; only the owner role mutates it. Monotonic: once stopped, old authority never becomes current again without deliberate fresh owner action. Preliminary work (started/admitted before STOP) is explicitly non-authoritative. Immediately before a covered irreversible effect, the gate reads **current authoritative standing** and commits-or-refuses in the **same atomic step**; the check happens at commit time, never earlier. One mechanical ordering: STOP_EFFECTIVE vs effect commit, monotonic sequence only, never wall-clock. STOP-first → refuse. Effect-first → honestly record PRE_STOP_COMMIT (the switch cannot undo it and does not pretend otherwise). Stale local receiver state is never sovereign. **Fail closed**: if standing cannot be established at finalization, the effect does not commit and the inability to check is recorded. Replay restores nothing (old credentials/artifacts/receipts/action IDs/admissions/epochs cannot resurrect stopped authority). Restart must not widen authority. Evidence must preserve STOPPED / ESCAPED / UNKNOWN path verdicts and separately classify PRE_STOP_COMMIT; refusal alone never proves effect absence; silence stays UNKNOWN.

Minimum interface is semantic-only (no language/serialization/framework prescribed): read current authority state (authoritative, not cache); issue owner STOP (establishes STOP_EFFECTIVE at a precise commit position); admit preliminary work (optional, non-authoritative); attempt final protected commit (atomic read-standing + commit-or-refuse); recheck standing at finalization; record decision + effect observation; emit evidence a separate checker can re-derive verdicts from. The frozen contract wording governs over paraphrase (`evidence/CONTRACT.md`).

The **frozen contract** (`portable/evidence/CONTRACT.md`) adds specifics: STOP state is durable, monotonic (0 = ACTIVE, ≥1 = STOPPED), survives restart; exactly one final consequence gate, every covered effect passes through it; no effect commits without the final-gate transaction; no transaction commits without reading current authoritative STOP standing inside it. STOP authority is "the owner's revocation of permission for covered effects; it is not a message the worker must obey." Mandatory shared evidence vocabulary (hash-chained, deterministic, prev-record binding): STOP_ISSUED, STOP_OBSERVED, POST_STOP_ATTEMPT, DECISION (ADMIT/REFUSE + reason), EFFECT_OBSERVED, EFFECT_ABSENCE_OBSERVED, UNKNOWN; a REFUSE/DECISION alone never establishes effect absence. 20 bounded STOP-vs-finalize races must show 0 forbidden orderings.

### IMPLEMENTER_CHECKLIST.md — what a receiver MUST check
The consequence (exact irreversible action) and the last reversible point before it — the final gate goes there. Current owner authority stored durably; worker must not be able to alter it via credential, cached copy, or restore. Exact event defining STOP_EFFECTIVE in the commit order. STOP ordered against final commit by monotonic sequence/tx-id/log-offset, never wall-clock. Stale-local-state receivers must still be refused at the final gate. Pre-STOP admissions re-checked before commit. Fail-closed on unavailable standing, recorded. Restart must not restore old authority. Old credential/receipt/artifact/action-ID/admission/epoch replayed as current authority must each be refused. Effect presence established by reading the effect store (absence = checked and found nothing — refusal alone proves nothing). A separate auditor reading only finished evidence must classify every path STOPPED/ESCAPED/UNKNOWN and must identify PRE_STOP_COMMIT as an ordering classification distinct from the path verdict.

### CONFORMANCE.md — seven paths, PASS
P1 already-running worker → STOPPED. P2 delayed/scheduled job → STOPPED. P3 outstanding authentic credential after STOP → STOPPED (authority gone; authenticity irrelevant). P4 pre-STOP artifact presented as authority → STOPPED. P5 successor actor claiming inherited/predecessor authority → STOPPED absent a fresh post-stop owner grant. P6 stale receiver cache says ACTIVE → STOPPED at the authoritative final gate (must not be "solved" by refreshing R2 first). P7 in-flight work, pre-STOP preliminary admission, STOP intervenes before irreversibility → STOPPED at the final gate (must not be solved by deleting the admission). PASS = 7/7 STOPPED per a separate auditor reading only finished evidence + independent effect-state verification wherever an effect could have occurred + unambiguous STOP/finalize ordering for every attempt + 20 races / 0 forbidden orderings. ESCAPED anywhere or UNKNOWN anywhere ⇒ no PASS; silence never counts. Impl A: `./RUN.sh` + `./VERIFY.sh` (7/7, evidence `evidence/frozen/`); Impl B: `python3 run.py` + `python3 auditor.py evidence/evidence.jsonl evidence/race_evidence.jsonl` (frozen evidence `portable/evidence/`).

### EVIDENCE.md — canonical fields
Eight fact kinds kept distinct: STOP issued (recorded; propagation not assumed); STOP effective (reached the serialization boundary, at its precise commit position); receiver/local view (may be stale; recorded so staleness is visible, never authoritative); final authority check (standing read at commit time); final decision (ADMIT/REFUSE + reason, at the gate); effect observed (effect store independently shows effect present); effect absence observed (store checked, effect absent); ordering evidence (monotonic commit position of every attempt/decision/effect, classifiable against STOP_EFFECTIVE). Records chained so tampering is detectable (each binds the previous); monotonic sequence only, no wall-clock. Verdicts STOPPED/ESCAPED/UNKNOWN + separate PRE_STOP_COMMIT ordering classification. "Semantic requirements, not a wire format — neither reference implementation's exact record layout is mandatory." Example record fields: hash, prev (GENESIS…), seq, type (DECISION), label (P1), payload {action_id, actor, decision, reason (e.g. ACTIVE_NO_STOP), authoritative_epoch, stop_journal_rowid, attempt_journal_rowid, note}. **No canonical wire fields for authority/proposal/effect identity are specified — deliberately implementation-neutral.** Semantic identities used: the monotonic commit position, action_id/actor, authority epoch, journal row positions.

## 4. wallet — owner authority / replacement / successor

- `README.md`, `SECURITY.md`: "The wallet carries the user's history. The receiving service decides what that history permits." OpenLine Wallet keeps user-owned authority history outside the AI provider; authority history = signed permission records, revocations, action receipts in a folder the user controls; exported JSON bundle is verifiable without calling the original provider. Security invariants: export bundles never contain private keys; **a principal root certifies the wallet epoch key; the epoch key may issue and strictly narrow mandates; root-signed revocation removes standing without changing the original mandate bytes**; a receiver pins the root outside the bundle, admits only fresh monotonic history, owns every consequential decision; holder presentations bind a subject key to one receiver challenge and one exact action; competing valid heads quarantine the principal rather than letting the gate invent consensus. Bundles expire: default 600-second ceiling (bounds stale-history exposure; revocation exposure before delivery remains possible inside the window). The model cannot approve itself.
- Receiving-service contract (README): store the user's public identity key at onboarding; check the bundle is signed by that key and **newer than the last accepted bundle** (older or conflicting versions refused); issue a one-time challenge tied to the exact action; return a signed `ALLOWED` or `STOPPED` receipt. `openline-wallet verify` checks evidence and prints `EVIDENCE_VALID` — authorization belongs to the receiving service.
- **Successor authority under the same owner-controlled rules** (`PLATFORM_EXIT_LIVE_001.md`, `APPROVED_JOB_LIVE_001.md`, `CREDENTIAL_OVERREACH_LIVE_001.md`): the owner revokes worker A, grants the same narrow scope to a different subject (agent-b / Codex) with a **distinct subject key and mandate ID** under the **same user principal and continuously signed history head**. Old signed authority remains authentic but loses standing ("a record can be genuine and still be too old to use"; MANDATE_OWNER-001's "historically authentic but implicitly superseded"). The successor holds the key named in the **current** permission and acts through the Receiver Gate, which makes each execution decision. The pre-switch receiver receipt stays in Wallet history. The Wallet itself has no policy authority; decision authority remains `RECEIVER_GATE`. The successor receives no prior chat, provider credential, or filesystem home; a descendant-of-verified-handoff candidate is admitted while a restart-from-base candidate is rejected. APPROVED-JOB-LIVE-001's short rendering: "The worker changed. The approved job did not restart, and the replacement did not inherit the previous provider's authority or private context."
- **Revocation/standing** (`AUTHORITY_IN_TIME_001.md`, `TEMPORAL_AUTHORITY_PROFILE_v0.md`, wallet README): three facts kept separate as evidence: REVOCATION_ISSUED (owner produced the authentic revocation), REVOCATION_OBSERVED (receiver incorporated it into current authority state), EFFECTS_CLOSED (outstanding work can no longer escape the applicable effect frontier) — none implies the others. Temporal admission rule: a receiver may label work `ADMIT_REVOCATION_PROTECTED` only if detect + propagation + receiver + stop + uncertainty bounds (one explicit unit, declared clock model) leave `remaining_margin > 0`; equality/negative margin/missing-unsupported bound/double-counted uncertainty ⇒ `REFUSE_REVOCATION_PROTECTION`. Revocation issued or observed after the cancellation cutoff must be recorded as late, never rewritten as prevention. `WALLET_EFFECT_CLOSURE_001.md`: preparation consumes the one-use holder challenge but cannot authorize the effect; the receiver revalidates the exact grant against its newest admitted standing inside the same lock as the ledger write; an ordinary `/admit` says `AUTHORIZATION_ADMITTED_ONLY`; `POST /close` returns signed `EFFECT_CLOSED` only with zero active frontiers and all matching pending tickets de-stood; exact ticket replay is idempotent in-process; crash/corruption seals the receiver (restart does not silently clear uncertainty).

## 5. Replay-sensitivity

**Claim replay resistance:**
- receipt-gate Verified Commit (`docs/VERIFIED_COMMIT.md`): 256-bit one-use code, domain-separated SHA-256 hash (`one_use_code_hash`) in the signed authorization; the ledger **atomically consumes** decision + code before callback invocation — sequential replay blocked; if callback throws or process dies after consumption, replay stays blocked. `replay_scope_hash`: distinct valid authorizations for the same receiver-defined effect identity cannot both run; the x402 Airlock derives it from (scheme, network, asset, payer, signature model, **nonce**). The bundled proof blocks changed tool/target/settings/run/capsule/evidence/policy, wrong one-use code, expired authorization, sequential replay, and one of two simultaneous uses.
- wallet: one-use holder challenges tied to the exact action (`README.md`, `SECURITY.md` invariant "one-time challenge tied to the exact action", `WALLET_EFFECT_CLOSURE_001.md` "preparation consumes the original one-use holder challenge"); receivers refuse older/conflicting history versions (a genuine-but-old record is unusable); bundle expiry (600 s default) bounds stale-history replay. `WALLET_CLOSURE_SET_001.md`: a signed set report is historical evidence for one exact request only — "never authorizes later effects"; a fresh request needs fresh receiver witnesses; negative controls included "a replay under a fresh request nonce".
- kill-switch: invariant 10 — "Replay does not restore authority": old credentials, artifacts, receipts, action IDs, preliminary admissions, or epochs cannot independently resurrect stopped authority (tested paths P3 outstanding credential, P4 pre-STOP artifact). P5: successor needs a fresh post-stop owner grant.

**Do NOT claim replay resistance:**
- olp-wire-canon receipts: no one-use, nonce, or freshness semantics anywhere in SPEC.md. The amendment chain has intra-chain replay hygiene (verifier must reject duplicate `amendment_sequence`; `previous_receipt_hash` continuity), but a valid receipt can be re-presented indefinitely — freshness is delegated to derived layers ("COLE metric equations, calibration profiles, thresholds, and actuation rules are outside Wire Canon 0.1").
- kill-switch evidence records carry no nonce/expiry wire field (ordering is monotonic sequence; replay resistance comes from the final-gate's atomic read-and-commit, not from the artifact).

## 6. Same semantic fact stated differently (mismatches)

1. **PASS criterion.** `kill-switch/portable/evidence/CONTRACT.md` §7: "For every covered path: post-stop authority refused before consequence, **or the evidence explicitly shows the path unresolved/escaped**." vs `kill-switch/portable/evidence/PREREGISTRATION.md` § Acceptance: "PASS requires ALL of: 1. **7/7 paths STOPPED** per the separate auditor" vs `kill-switch/portable/CONFORMANCE.md`: "PASS requires **every covered path to be STOPPED**… If any path is ESCAPED, the run does not PASS. If any path is UNKNOWN, the run has not established PASS." The frozen contract's §7 wording tolerates an "explicitly unresolved/escaped" showing as a per-path alternative; the other two demand all-seven STOPPED. (GATE_CONTRACT.md declares the frozen copy governs.)
2. **How fixed is the evidence vocabulary.** `kill-switch/portable/EVIDENCE.md`: "Semantic requirements, **not a wire format — neither reference implementation's exact record layout is mandatory**." vs `kill-switch/portable/evidence/CONTRACT.md` §5: "**Every implementation emits the same shared vocabulary** (hash-chained, deterministic, with prev-record binding): STOP_ISSUED, STOP_OBSERVED, POST_STOP_ATTEMPT, DECISION, EFFECT_OBSERVED, EFFECT_ABSENCE_OBSERVED, UNKNOWN."
3. **Record names for the same facts.** EVIDENCE.md's 8 plain-English types ("STOP issued", "**STOP effective**", "Receiver/local view", "Final authority check", "Final decision", "Effect observed", "Effect absence observed", "Ordering evidence") vs CONTRACT §5's vocabulary (STOP_ISSUED, **STOP_OBSERVED**, POST_STOP_ATTEMPT, DECISION, EFFECT_OBSERVED, EFFECT_ABSENCE_OBSERVED, UNKNOWN). "STOP effective" vs "STOP_OBSERVED" is the sharpest name clash; "Ordering evidence" exists as a record type in EVIDENCE.md but not in CONTRACT §5 (ordering there is the per-record prev-binding + monotonic seq).
4. **UNKNOWN as record vs verdict.** Same frozen `CONTRACT.md`: §5 lists "UNKNOWN — the appraiser cannot determine the state from the evidence" as an **emitted record type**, while §9 says the appraiser produces UNKNOWN as one of exactly three **verdicts** per path. It is unclear whether an implementation emits UNKNOWN records or only the auditor assigns UNKNOWN.
5. **"Observed" means different events.** `wallet/TEMPORAL_AUTHORITY_PROFILE_v0.md`: REVOCATION_OBSERVED = "the **relevant receiver incorporated** that revocation into its current authority state" (receiver-side event). `kill-switch/portable/evidence/CONTRACT.md` §5: STOP_OBSERVED = "STOP_EFFECTIVE **reached the serialization boundary**" (owner-side commit event). Same word, different point in the chain — the wallet's observed-state requires receiver incorporation; the kill-switch's is satisfied at the serialization boundary.
6. **Two claim-boundary documents.** `receipt-gate/CLAIM_BOUNDARY.md` (77 lines, root) vs `receipt-gate/docs/CLAIM_BOUNDARY.md` (299 lines). Both are "the" claim boundary for v0.6.0rc6 but frame supported claims differently: the root file enumerates COMMIT/QUARANTINE/DENY appraisal + warning-time fixtures + the rejected v0.5.0rc3 result; the docs version leads with "signed action receipts and a pinned Assay evidence bundle converted into deterministic, signed policy decisions" and a fuller supported/not-established list. A reader cannot tell which is authoritative.
7. **Byte-vs-character notation for signature fields (hazard, not contradiction).** `olp-wire-canon/SPEC.md` §2 example shows `"public_key": "32-byte-lowercase-hex"`, `"value": "64-byte-lowercase-hex"`; §4 requires 64 and 128 **hex characters** respectively. `receipt-gate/docs/RECEIPT_SCHEMA.md` repeats the byte notation ("32-byte lowercase hex" / "64-byte lowercase hex"). Byte notation and character notation agree (32 bytes = 64 hex chars), but an implementer reading only the examples could emit 64-character public keys.
8. **Wire-canon envelope vs receipt-gate v0.4 receipt body.** SPEC.md §2: the signed body MUST contain `spec_uri`, `attestation`, `capture_status`. The documented v0.4 `proof_to_policy_decision_receipt` (`docs/RECEIPT_SCHEMA.md`) contains none of those three — it is a different application profile, but no doc states explicitly whether the wire-canon envelope rule (remove exactly `payload_hash` + `signature` before hashing) applies to v0.4 decision receipts, or what the v0.4 signed-body construction is.

## 7. Implementability from docs alone (per dimension)

- **Signature scheme — DEFINED.** Ed25519, lowercase hex encodings, and the critical rule (sign canonical body bytes directly, never `payload_hash` or the envelope) are unambiguous in olp-wire-canon. Caveats: the §2/§4 byte-vs-char notation hazard (§6.7); the v0.4 decision receipt's signed-body rule is not restated in receipt-gate docs (§6.8); legacy v0.2/v0.3 decision-receipt field sets are not documented (verifiers accept them, docs don't define them).
- **Canonicalization — DEFINED.** `olp-canonical-json-int-v1` is fully specified (key ordering, whitespace, escapes, ASCII output, integer range, duplicate-key rejection, no floats). The `$int`/`$f64` normalization and "signed bodies MUST remain valid canonical JSON" are clear. Receipt-gate decision receipts reference the same canonicalization ID; byte-identical reproduction is achievable from the wire-canon text.
- **Standing claim fields — VAGUE.** What travels is described semantically (signed projection; sequence + predecessor; hash of support artifact; hash of the exact protected call; freshness window; terminal REVOKED/INACTIVE admitted through `admit` successor rules; STOP_EFFECTIVE = monotonic head sequence). But exact JSON field names, the terminal-state record format, and the freshness-window representation are not pinned in any public doc; PORTABLE_STANDING_CLAIM.md cites implementation module names (`olp_gate.stop_standing.derive_path_verdicts`) for verdict re-derivation. A third party could implement the *checks* from the docs but not byte-compatible admission records.
- **Receipt fields — DEFINED for v0.4 decision receipts and wire-canon capture receipts.** `docs/RECEIPT_SCHEMA.md` gives the complete v0.4 field set including the Verified Commit authorization block; the wire-canon `schemas/` directory pins strict JSON Schema 2020-12 profiles per kind. **VAGUE for the wallet v1 decision receipt**: docs (`WALLET_EFFECT_CLOSURE_001.md`, `AUTHORITY_IN_TIME_001.md`) reference "the v1 Wallet decision receipt schema" and state it is preserved/unchanged, but no doc I read spells out its field list — cannot confirm implementability from docs alone.
- **Effect identity — DELIBERATELY UNDERDEFINED.** Kill-switch specifies none at the wire level by design ("semantic operations only"; identities are monotonic commit position + action_id/actor + journal rowids). Receipt-gate Verified Commit makes it receiver-defined: `replay_scope_hash` with a fully specified x402 derivation (scheme, network, asset, payer, signature model, nonce) but "a generic caller is responsible for deriving any replay scope correctly" — i.e., undefined for generic use. Wallet binds "exact effect ID and actual effect result" in the final receipt without specifying the ID format. A third party can implement the *check pattern* (bind effect identity, consume atomically) but not a portable effect-identity wire format — which is consistent with the stated non-goal "A standard" (GATE_CONTRACT.md).

## Caveats on this survey
- Scope was restricted to docs/schemas/vectors/examples per instructions; implementation source, test files, and study-internal evidence JSON were not read, so field lists above come from prose + JSON Schema + fixture filenames, not from code.
- Wallet has no `schemas/` directory; receipt-field detail for the v1 wallet decision receipt was not found in the docs read — flagged in §7 rather than asserted.
- The root `receipt-gate/CLAIM_BOUNDARY.md` vs `docs/CLAIM_BOUNDARY.md` split and the kill-switch EVIDENCE.md vs frozen CONTRACT.md splits (§6) are the substantive inter-document mismatches relevant to any interop implementation.
